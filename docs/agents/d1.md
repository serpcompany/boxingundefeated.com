# D1

Boxer data lives in D1, through the Drizzle schema in `packages/data-ops` and the migrations in
`d1/drizzle/`. Read this before changing the schema, running a migration or an import, or deploying
to an environment. The SERP
[D1 migration and promotion](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/database-management-promotion-drizzle-d1.md)
and [Data and storage](https://github.com/serpcompany/serp/blob/main/docs/engineering/standards/web-stack/data-and-storage.md)
standards apply. The query and importer tests are in the inner loop in [AGENTS.md](../../AGENTS.md).

## Data source

The pipeline's `boxers.json` (about 104 MB) is the only boxer data source. Each version is pinned
in R2 at `boxers/<version>.json`, where the version is the file's SHA-256, and is never
overwritten: one private bucket per environment, `boxingundefeated-com-data-staging` and
`boxingundefeated-com-data-production`, bound to no Worker (`scripts/d1/artifact.ts`). Local copies
live in `from-pipeline/` (gitignored). Only `db:import`, `db:parity` and the artifact scripts read
the file; builds read no boxer data. `gh run list --workflow d1-import.yml` names the versions
imported so far.

## Boxer photos

Pages show no image from boxrec.com (#64). Each photo is copied once into the environment's
private photo bucket, `boxingundefeated-com-photos-staging` or `-production` (local:
`-photos-local` in Wrangler's local state), bound to the Worker as `PHOTOS`, which only reads it
and serves `/photos/<sha256>.<ext>` ([worker.md](worker.md)). The key is the SHA-256 of the bytes
and the image type they show, so an object is never overwritten with other content. The D1 table
`photos` maps each copied source URL (a boxer's `avatar_image`) to its key; the page queries join
it, and a boxer without a row, or with BoxRec's placeholder, gets the site's placeholder.

`pnpm db:copy-photos -- --target <env> [--source <boxers.json>] [--limit <n>] [--max-minutes <n>]`
(`scripts/d1/copy-photos.ts`) copies the photos D1 doesn't record yet: one request at a time, at
most 2 a second, with an identifying user agent; it honours `Retry-After`, stops after 25 refusals
in a row (403, 429, 5xx), and prints the copied, failed and remaining counts. It uploads before it writes D1, so a
row always names an object that exists. Locally, `--target local --limit 50` fills Wrangler's
local R2 and D1 for `pnpm preview:worker`. Staging and production run it only in `d1-import.yml`.

## Commands

- `pnpm db:generate`: the migration for a `schema.ts` change (commit both); a re-run reports none.
  It mangles expression indexes: hand-write those (0002 says how). Never `drizzle-kit push`, and
  never edit `d1/drizzle/meta/`.
- `pnpm db:check`: `drizzle-kit check`, that the migration snapshots form one chain (two branches
  that each ran `db:generate` fork it). Part of `pnpm check`; CI's migration job runs it too.
- `pnpm db:migrate:local`, `pnpm db:migrations:list:local`: apply or list migrations on the local
  D1 in `apps/web/.wrangler/state`, which the local Worker uses. `pnpm db:reset:local` wipes it,
  migrates and seeds the fixture (`db:seed:local`), in seconds.
- `pnpm db:fetch-artifact -- --target staging --version <sha256>`: download a pinned version to
  `from-pipeline/boxers-<version>.json` and check its SHA-256 (your Wrangler login reads the
  bucket). Then `pnpm db:import -- --target local --source <that file>` loads it idempotently into
  the local D1, and `pnpm db:parity -- --target local --source <that file>` proves it.
- `pnpm db:upload-artifact -- --target staging --source <boxers.json>`: pin a new pipeline output.
  It validates the file, uploads it unless the bucket already holds it, refuses a key that holds
  other content, reads the upload back and prints the version.
- `--target local` on both artifact scripts uses Wrangler's local R2, to try the flow offline.
- `db:{migrate,migrations:list}:{staging,production}` use `--remote --env <env>`; never `--preview`.

## Remote imports (CI only)

Staging and production D1 change only through CI: migrations in `ci.yml`'s deploy jobs, imports in
`.github/workflows/d1-import.yml`. Agents never run a `--target staging|production` or `--remote`
D1 command from their own machine, and never dispatch, re-run or approve `d1-import.yml`; the
owner does. The workflow fetches the version from that environment's bucket, checks its SHA-256,
refuses a D1 missing one of the commit's migrations, then runs `db:copy-photos` (at most 35
minutes; [Boxer photos](#boxer-photos)), checks the tip again, and runs `db:import` (with its prune
cap), `db:parity` and `db:check-deployable`, and puts the photo counts and the parity report in
the run summary. The photos go first so that the import's finish, which moves the page cache to a
new generation, renders pages with them. Its preflight
(`.github/scripts/verify-d1-import.sh`) refuses while a `ci.yml` deploy of that environment runs,
waits for approval or waits for its checks, and each import job checks that again right before its
D1 steps. The reverse holds too (#104): right before its migrate step, each `ci.yml` deploy job
refuses while an unfinished `d1-import.yml` run from any branch has a run-name that names its
environment, or no environment (`verify-d1-import.sh --imports-only`), and then while
`dataset_state` shows an import in progress (`db:check-deployable --importing-only`, read-only). So
a migration and an import never write the same D1 at once; whichever refuses, the owner re-runs it
once the other finishes. Both run checks list only unfinished runs, one query per status, so
finished runs never block them, and they refuse when one status has more than 100. Each import job
also refuses unless its branch (`staging` or `main`) is still at the commit the run checked out,
before its first Cloudflare step and again before its D1 steps, because an approval wait or a queue
can outlast a merge: re-dispatch from the new tip.

1. Pin the file: `pnpm db:upload-artifact -- --target staging --source <boxers.json>`.
2. Staging, after the deploy of the commit has migrated it:
   `gh workflow run d1-import.yml --ref staging -f environment=staging -f version=<version>`.
   A clean run leaves the receipt `passed-d1-import-staging-<version>` (90 days).
3. Production, from `main` once the workflow and the code are promoted there:
   `gh workflow run d1-import.yml --ref main -f environment=production -f version=<version>`. It
   refuses a version without a staging receipt from a run on a commit that is on `staging`, then
   waits for the owner's approval of the `production` environment. It fetches the version from
   the production bucket, or, the first time, copies it there from the staging bucket (production
   buckets change only through CI), and passes `--confirm-production`, which records that
   approval.

`allow_prune=<n>` lets one run prune up to `n` boxers, at most 250, instead of the cap (staging
1 %, at most 50; production none). It shows in the run's name and the preflight's summary, so the
approver sees it; a larger prune needs a change to the preflight script. The token in each
environment's `CLOUDFLARE_API_TOKEN` needs D1 Edit and Workers R2 Storage Edit on the SERP account.

## Deploy gate

The Worker reads every boxer page from D1: profiles, listings, divisions, the homepage and the
HTML sitemap (503 until an import finishes). Deploy to an env only once
`pnpm db:check-deployable -- --target <env>` passes and `db:parity` is clean there; for staging
and production, a clean `d1-import.yml` run shows both.

A deploy of an environment that starts while an import into it runs or is pending refuses before it
migrates (Remote imports above); the owner re-runs the deploy once the import finishes. The
importing flag can't tell a running import from one that stopped before it finished, so after a
failed import the deploys refuse until an import finishes: re-run it first. If that import refuses
because the D1 lacks a migration of the branch's new tip, the owner applies the migrations
(`pnpm db:migrate:<env>`), then re-runs the import and the deploy.
